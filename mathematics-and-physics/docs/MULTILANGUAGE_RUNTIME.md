# Multi-language code runner — Issue #24

This stage adds an **operator-only** local execution and debugging engine for
the Engineering AI Lab's locally trained text model. It is **not** a public
code execution website and no API route is added. Neither the web application
nor the training worker receives Docker daemon access.

## Available language adapters

| Language | Local Docker runtime | Entry file |
| --- | --- | --- |
| Python | `python:3.12-alpine` | `main.py` |
| JavaScript / Node.js | `node:22-alpine` | `main.js` |
| C | `gcc:14` | `main.c` |
| C++ | `gcc:14` | `main.cpp` |
| Go | `golang:1.24-alpine` | `main.go` |
| Rust | `rust:1.86-alpine` | `main.rs` |
| Java | `eclipse-temurin:21-jdk-alpine` | `Main.java` |
| Ruby | `ruby:3.3-alpine` | `main.rb` |
| PHP | `php:8.3-cli-alpine` | `main.php` |

They are **supported configurations**, not a claim that every library,
package, build tool, language variant or feature works. The CI smoke suite
runs Python, JavaScript, C and C++; the remaining languages require additional
runtime validation before production use. New languages are registered in
`code_runtime/runner.py` after sandbox and functional testing. The model
cannot execute *all programming languages* without their respective
compilers/interpreters.

## Prepare once (trusted machine with Docker installed)

From `mathematics-and-physics`:

```bash
docker pull python:3.12-alpine
docker pull node:22-alpine
docker pull gcc:14
docker pull golang:1.24-alpine
docker pull rust:1.86-alpine
docker pull eclipse-temurin:21-jdk-alpine
docker pull ruby:3.3-alpine
docker pull php:8.3-cli-alpine
python -m code_runtime.cli --languages
```

These image downloads happen only when **you** run `docker pull`. The
execution tool itself uses `--pull=never`; it never fetches packages or
images dynamically in response to generated code.

Run an existing local file:

```bash
python -m code_runtime.cli --file /path/to/main.py --stdin "Alice"
python -m code_runtime.cli --file /path/to/main.cpp --language cpp
```

Run and optionally correct code generated by **our own trusted checkpoint**:

```bash
python -m code_runtime.cli --checkpoint /path/to/checkpoint.pt \
  --language python --prompt "Write a palindrome checker" --fix-attempts 2
```

This action must be invoked by the trusted local owner. The code-generation
model itself is small and experimental; it may generate incorrect or unusable
programs. An exit code of zero means the process ran successfully, **not**
that it solves the request correctly. Always test actual outputs and
requirements. The generated code is never committed to Gitea automatically.

## Containment strategy

Every attempt starts a freshly named Docker container with no network,
read-only root filesystem, read-only mounted source/stdin files, temporary
sandbox-only writable `/tmp`, no database/model/Gitea mounts, no host
project mounts, no Docker socket, no added capabilities, non-root UID,
`no-new-privileges`, strict process/memory/CPU limits, a 20-second maximum
wall clock time, and a combined 32 KiB stdout/stderr cap. The runner removes
its own container on timeout or excessive output.

Source files are at most 64 KiB; supplied standard input at most 8 KiB.
The language and shell command are chosen from a fixed registry. Source text
and user inputs are never inserted into shell commands. Package installation,
external dependencies and network APIs are unavailable during execution.

**Important:** A Docker container is not a perfect security sandbox.
Only use this on a trusted and patched local Docker host. Do not expose this
tool to untrusted users, enable privileged containers or attach sensitive
volumes. If arbitrary code execution is needed for other users, implement
a separate approval queue and stronger VM isolation first.

## Roadmap

- Real smoke tests for Go, Rust, Java, Ruby and PHP runtimes.
- Functional correctness benchmarks and model-aware debugging evaluation,
  not just command exit codes.
- Owner-approved read-only source snapshots from Gitea, per-task artefacts
  and reviewed fixes in Git.
- Optional local UI to preview generated code before submitting a job to a
  separately isolated execution broker. No unrestricted web code runner.
- Stronger VM/microVM isolation and strict language-specific resource
  accounting for multi-user environments.
